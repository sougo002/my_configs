# 共有レビュープロセス

このドキュメントは `review-pr`、`self-review` スキルから参照される共通のレビューロジックを定義する。
単体ではスキルとして機能しない。

## 前提条件

呼び出し元スキルが以下を準備すること:

- **作業ディレクトリ**: worktreeまたはリポジトリのパス
- **ベースブランチ名**
- **変更ファイル一覧**: `git diff --name-status <base>...HEAD` の出力
- **diff**: `git diff <base>...HEAD` の出力

## 並列レビュー（サブエージェント）

以下の4つのサブエージェント（Agent ツール, model=opus）を起動する。
**重要: 4つの Agent ツール呼び出しを必ず1つのレスポンス内でまとめて行うこと。これにより並列実行される。**

各サブエージェントには変更ファイル一覧・diff・作業ディレクトリのパスを渡す。
サブエージェントの作業ディレクトリは呼び出し元が指定した作業ディレクトリとする。
サブエージェントは必要に応じて Read で完全なソースコードや周辺コードを確認する。

| サブエージェント | 観点 | チェック項目 |
|-----------------|------|-------------|
| ロジック・データ整合性 | 考慮漏れ、境界条件、データ破壊 | 後述 |
| セキュリティ・認可 | 脆弱性、認証、権限外アクセス | 後述 |
| 設計・コード品質 | 設計原則、可読性、エラーハンドリング | 後述 |
| テスト | カバレッジ、テスト品質 | 後述 |

### サブエージェント共通指示

各サブエージェントのプロンプトは以下の共通部分 + 観点別指示で構成する。

```
以下の変更をレビューしてください。出力は日本語で行うこと。

## 観点
[観点名]

## プロジェクト固有ルール
作業ディレクトリの `.claude/CLAUDE.md` が存在する場合は読み込み、
自分の観点に関係するルールファイルを判断して Read すること。
それをレビュー基準として優先的に使用すること。

## 変更ファイル一覧
[git diff --name-status の出力]

## diff
[git diff <base>...HEAD の出力]

## レビュー範囲
**レビュー対象は diff に含まれる変更行のみとする。**
- 変更されていない既存コード（他の関数、テストケース、ファイル等）に対する指摘は行わないこと
- ただし、今回の変更によって新たに生じた問題（変更行が参照する値の不整合、変更が原因で発生するバグ等）は指摘すること
- 周辺コードの Read は、変更行の正しさを判断するための文脈理解にのみ使用すること

## チェック項目
[観点別チェック項目]

## 出力形式
重大度（Critical/High/Medium/Low）と共に所見を箇条書きで報告すること。
良い実装があれば併せて報告すること。
```

### 観点別チェック項目

#### 1. ロジック・データ整合性

```
以下の観点で変更をレビューすること。

- **境界条件・考慮漏れ**: null/None/空文字/空リスト/0 の扱い、off-by-one、想定外の入力パターン
- **状態遷移**: ステータスやフラグの変更が全ての遷移パスで正しいか、到達不能な状態が生じないか
- **競合・並行処理**: 同一リソースへの同時アクセス、楽観的ロック/排他制御の有無、非同期処理のエラーハンドリング
- **データ破壊・消失**: DELETE/UPDATE の WHERE 条件の妥当性、カスケード削除の影響範囲、ロールバック漏れ
- **トランザクション整合性**: commit/rollback の範囲が適切か、部分的な更新で不整合が残らないか
- **副作用の波及**: 変更が呼び出し元・他機能に意図しない影響を与えないか
```

#### 2. セキュリティ・認可

```
以下の観点で変更をレビューすること。

- **インジェクション**: SQL/NoSQL インジェクション、XSS、コマンドインジェクション、パストラバーサル
- **認証チェック漏れ**: 認証が必要なエンドポイントで認証が適用されているか
- **認可・権限チェック漏れ**: 操作対象リソースに対する権限検証が行われているか、管理者/一般ユーザーの区別
- **テナント分離**: クエリに tenant_id 条件が含まれているか、他テナントのデータにアクセスできる経路がないか
- **機密データの露出**: パスワード、トークン、個人情報がログ・レスポンス・エラーメッセージに含まれていないか
- **入力検証**: 外部入力（リクエストパラメータ、ファイルアップロード等）が検証されているか
```

#### 3. 設計・コード品質

```
以下の観点で変更をレビューすること。

- **責務分離**: 1つの関数/クラスが複数の責務を持っていないか、レイヤー間の責務境界が守られているか
- **依存関係**: 不適切な層間依存、循環依存がないか
- **エラーハンドリング**: エラーが握りつぶされていないか、適切なエラーレスポンスが返されるか
- **可読性**: 命名の明確さ、ネストの深さ、関数の長さ
- **パフォーマンス**: N+1クエリ、不要なループ内DB/API呼び出し、大量データの一括読み込み
```

#### 4. テスト

```
以下の観点で変更をレビューすること。

- **カバレッジ**: 変更されたロジックに対応するテストが存在するか、新規パスにテストが追加されているか
- **境界条件テスト**: null/空/上限値などの境界条件がテストされているか
- **テナント分離テスト**: 他テナントのデータにアクセスできないことを検証するテストがあるか
- **異常系テスト**: エラー/例外パスのテストがあるか（存在しないリソース、権限なし、バリデーションエラー等）
- **テストの独立性**: テスト間で状態が共有されていないか、実行順序に依存していないか
```

## 妥当性検証

サブエージェントから返された各指摘について、実際のコードを確認し妥当性を検証する。

各指摘に対して以下を行う:

1. **該当箇所の確認**: 指摘が参照するファイル・行を作業ディレクトリ上で Read し、指摘内容が実際のコードと一致するか確認する
2. **文脈の確認**: 必要に応じて周辺コード・呼び出し元・型定義などを確認し、指摘が正しい前提に基づいているか検証する
3. **判定**: 各指摘を以下のいずれかに分類する
   - **採用**: 指摘が妥当。そのまま結果に含める
   - **修正**: 指摘の方向性は正しいが、詳細や重大度に誤りがある。修正して含める
   - **却下**: 誤検知、または変更範囲外の既存コードへの指摘。結果から除外する

### 却下基準

以下に該当する指摘は除外する:

- 実際のコードと異なる前提に基づいている（存在しない変数・関数への言及、型の誤認など）
- diff に含まれない既存コードへの指摘（レビュー範囲の指示に反するもの）
- フレームワークやライブラリが既に保証している事項への冗長な指摘
- 同一の問題に対する重複した指摘（最も適切な1つに集約する）

## レビュー優先度

| 優先度 | 基準 | 例 |
|--------|------|-----|
| Critical | マージ前に必ず修正 | セキュリティ脆弱性、データ消失リスク、破壊的変更 |
| High | 修正すべき | 設計原則違反、エラーハンドリング欠如、パフォーマンスボトルネック |
| Medium | 修正を検討 | スタイル不統一、テスト不足、技術的負債 |
| Low | 提案 | 命名改善、ドキュメント不足、軽微なリファクタリング |
